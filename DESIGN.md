# NHI demo design contract

This public presentation snapshot preserves the approved NHI component system and focused Patrick journey. It does not expand the whole website.

1. **One case, three acts.** Understand the pulley → Build the inquiry → Move the case forward. F-4412 and the original mounting question provide continuity.
2. **One chronological example.** Inquiry / v1 start at 200 units; the change requests 250 units and five weeks; example v2 shows 250 units and a $2,260 priced subtotal. The existing workspace's later 250-to-300 request is a distinct follow-up example.
3. **Explicit transitions.** Saving an inquiry, issuing a quote, saving a change, requesting review and confirming acknowledgement retain their review boundaries. Viewing a scene does not create a record.
4. **Original evidence stays intact.** Preserve question identity, exact wording, source, attachments, quotation version and request / reply lineage. An acknowledgement does not resolve engineering questions.
5. **Known, requested and confirmed are separate.** Catalog A/B/D support dimensional facts. Illustrative hub geometry does not prove fit. Five-week delivery is requested and unconfirmed; six-to-eight-week timing is conditional. Freight, tax and engineering suitability remain open.
6. **Task hierarchy.** Each scene leads with its current question or outcome and one main continuation. Show buyer / seller role and the next owner at a handoff. The final plan names customer information, engineering review and seller coordination.
7. **Visual roles.** Silver / white carry work and document surfaces; graphite carries text and the contained equipment stage. Lime with dark text is the primary action. Calm blue carries the retained question / review context. Selection and focus stay neutral; examples and errors remain explicitly labeled.
8. **Consistent components.** Reuse React, shadcn-derived source and Base UI controls. One sans family, aligned field grids, fixed unit suffixes and readable selected / invalid states apply across the presentation.
9. **Phone prioritizes the task.** Show the current problem and input first; open 3D on demand. Opening focuses and positions the labeled model stage; closing focuses and positions the current question. Neither action opens the phone keyboard or saves a requirement. Keep a useful next / back action available. In a quote, amount and delivery precede the retained question; detailed lines begin collapsed on phone and expanded on desktop.
10. **Prepared replay is honest.** The short route reads four scenes prepared from the same case. Scene navigation is not presented as executing skipped business actions.
11. **Capability preview is a separate sample.** Label the crank mechanism and optional Annora platform scope. Retain Return to F-4412. Put its entrance in a secondary optional appendix and Guide, after the business outcome; it is not the case's primary next action. Do not claim its motion or Studio publication as an implemented NHI production capability.
12. **Storage and history.** Keep existing workspaces independent. Archive previous presentation runs before starting another. Block stale-tab replacement; retain export actions. The capability snapshot prefixes localStorage, sessionStorage and IndexedDB names.
13. **Offline fallback is explanatory.** Six readable scenes, clearly labeled stills, the prepared fixture and English scripts accompany the demo. Static cards do not run the model or issue transactions.

14. **The business journey has a real ending.** The completed plan leads with Prepare application information: mounting, operating speed and radial load. The exact quotation and retained original question support that next step; the saved seller acknowledgement can be read in place. Engineering and seller responsibilities follow. The ending uses a secondary case export and explicit customer next-step text, rather than a primary capability-tour button. Viewing or exporting does not transmit application data.
15. **Phone capability uses one visible application surface.** Explorer and Studio occupy a focused full viewport, with sample identity and Return to F-4412 always visible. The host document does not compete for vertical scrolling. Studio's customer preview is shown directly in a sibling frame; Studio stays mounted but hidden and inert so its real saved draft, preview and release-review state remain intact. There is only one visible app scroller.
16. **Editor and customer view have explicit returns.** The direct customer view offers Back to Studio and Review release. Both invoke the existing Studio actions; they do not reconstruct publication state or bypass review. The native customer Return to Studio uses the same handoff. Resizing does not reload the editor or discard an unsaved draft. A slow or failed handoff offers an actual recovery link.
17. **The mobile handoff is presentation-only.** The bridge is query-gated, validates exact origin and source frame, and accepts only the defined preview identity, page and command allowlists. It changes navigation and focus only. It does not read or write business stores, resolve engineering questions or transfer the crank example to F-4412.

The [mobile refinement reference lock](docs/mobile-refinements.md) records the existing NHI target, user-observed problems and bounded device-preview references. Browser and online evidence is recorded separately; these rules alone are not final user visual acceptance or a physical-device performance claim.
